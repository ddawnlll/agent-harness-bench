# Methodology

This document describes the experiment behind `results/publication-data.json`,
its grading rules, isolation and accounting, and the exact definitions of every
published number. No number appears here that is absent from that file or its
sealed source.

## 1. Design

**Question:** given one model, one provider, one reasoning effort and three
engineering tasks, how do three coding agents perform, and at what cost in time,
CPU, memory and tokens?

- 3 agents × 3 tasks × 1 trial = 9 trials.
- Agents run concurrently within a round; one round per task.
- Grading is independent and runs after every agent in the round has exited.
- n = 1 per cell: the design screens, it does not estimate variance.

Rounds ran in fixed order: `r1-safety` (T1), `r2-performance` (T2),
`r3-coordinator` (T3). Each round has a 1680 s (28 min) deadline; the global
watchdog is 7200 s and was never approached. Total measured wall time, from
round 1 start to the last grade, was 2006.2 s.

## 2. Tasks

Each task is a git repository at a pinned start commit, delivered as a fresh
workspace with `TASK.md` and public tests. Hidden tests, oracle patches and
negative controls live outside every agent-readable tree.

| ID | Title | Start commit | What it tests | Public tests | Hidden cases | P0 gates |
|---|---|---|---|---|---:|---:|
| T1 | Cross-module execution safety | `18559cc3` | A position is protected only when an `ACTIVE` stop covers the open size, under partial fills, delayed acks, cancel races, stale callbacks, identity mismatch and restart | public suite | 16 (`h01`–`h16`) | 9 |
| T2 | Replay performance under parity | `390b675f` | Exceed 3× on a large replay workload while keeping byte-identical output, on hidden small, large, adversarial and fresh profiles | 53 | 16 checks over 4 workloads | 10 |
| T3 | Crash-safe job coordinator | `4b4f88d0` | Atomic claims, lease expiry, bounded retries, `SIGKILL` recovery, corrupt-state repair, idempotent completion | public suite | 25 (`F*`, `C1`–`C6`, `T*`, `M*`, `S_*`) | 10 |

T1's nine gates are premature protection, fail-closed, fill attribution,
protection loss, restart fidelity, cancel race, native identity, test integrity
and no shortcut. Its hidden suite imports only the documented public API
(`v9.Engine`, `v9.RecordingBroker`), and no workspace contains a hidden test.

T2 hidden workloads are generated by `hidden_cases.py` from unseen seeds; the
candidate cannot import or influence it. Parity is checked on `h_large`,
`h_adversarial`, `h_small` and `h_fresh`. The pristine baseline is a bundled
`git archive` export of the start commit, so it cannot be tampered with.

T3's 25 cases include `F1`–`F10`, `C1`–`C6`, `T1`–`T2`, `M1`–`M5` and
`S_TESTS`, `S_IMPORTS`, `S_MEMDB`. Concurrency stress runs 8 workers against 200
jobs, twice.

## 3. Rubric and P0 gates

A **verified pass** requires every P0 gate to pass *and* a score ≥ 80. A P0
failure cannot be compensated by a high score.

**T1 (100).** Correctness/adversarial 50, safety invariants 25, regression 15,
maintainability 10. Correctness and safety points are proportional to earned
case weight. `h07` (stale-callback guard) has weight 3 of 31 safety weight, so
failing it costs 25 × 3/31 = 2.42 points, and it also fails the
`G4_PROTECTION_LOSS` P0 gate, which overrides the total.

**T2 (100).** Correctness 40, performance 35, memory 15, maintainability 10.
With `S_large`, `S_adv` the median speed-ups and `r` the candidate/pristine
peak-RSS ratio on the large profile:

```
performance = 25 * clamp((S_large - 1.2) / 1.8) + 10 * clamp((S_adv - 1.2) / 1.3)
memory      = 15 * clamp((1.5 - r) / 0.7)
```

`clamp` restricts to [0, 1]. Changes below 1.2× are inside a declared noise
dead band; 3.0× large and 2.5× adversarial earn full marks. Performance is
zeroed if parity, determinism, contract or anti-trick gates fail. Correctness is
parity 22 + public tests 6 + pristine tests 6 + determinism 3 + contract 3.
Maintainability is 2 each for intact tests, retained suite size, no debug prints
and ≤1500 changed lines, plus 1 each for no forbidden imports and no fixture
changes.

**T3 (100).** Functional 40, concurrency/recovery 35, tests 15, maintainability
10; all ten P0 gates must pass.

**Determinism.** T1 and T3 run the hidden suite twice and invalidate the grade
if outcomes differ. T2 repeats each measurement three times, requires
byte-identical output, and records distinct outputs per workload. All nine
trials reported agreement.

## 4. Oracle and negative-control validation

Before the measured run, each grader was validated against known-good and
known-bad solutions (`graders/*/validation_report.json`):

| Grader | Oracle | Seeded baseline | Negative controls |
|---|---|---|---|
| T1 | PASS 100.0, 3/3 | FAIL 22.03, gates G1–G7 fail | 8 broken variants, each fails its intended gate |
| T2 | PASS 98.85 / 98.78 / 98.85, large 4.70–6.78× | FAIL 60.71, large 1.076× | 7 wrong implementations, all expectations met |
| T3 | PASS 100.0, 3/3, identical case signature | FAIL 38.0, six P0 gates fail | 7 variants, each fails its expected gate |

This shows the graders can pass a correct solution, fail the shipped defect and
fail specific wrong behaviours for the intended reason. It does not prove the
case set is exhaustive.

## 5. Execution and isolation

All three agents in a round start from one barrier. The controller prepares each
workspace, starts one process per trial in its own transient systemd user scope,
then releases the barrier. Launch jitter — barrier release to process exec — was
2.521–14.029 ms and is published per trial.

Per-trial scope settings, identical for all agents:

- `MemoryMax=3GiB` (3221225472 bytes)
- `CPUQuota=200%` (200000/100000)
- `TasksMax=4096`
- `taskset` affinity to one core pair: `0,1`, `2,3` or `4,5`.

The host exposes 6 logical CPUs. Pairs rotate per round so each agent occupies
each pair once (mapping in [FAIRNESS.md](FAIRNESS.md)). The cgroup `cpuset`
controller was unavailable in the delegated session, so affinity is enforced by
`sched_setaffinity`, not `AllowedCPUs`; it is advisory placement, not a hard
partition. Each workspace has its own `HOME`, `XDG_*`, `TMPDIR`, fresh checkout
and no git remote.

## 6. Relay accounting

Every model request from every agent and subagent traverses a loopback relay
bound to that trial. The relay injects the upstream credential and required
client headers (agents hold a dummy token), pins the model to
`deepseek-v4.1-flash` and the effort to `low` (rewriting when omitted), and
records metadata, tokens, HTTP status and duration. It never persists request
bodies, prompts, responses or authorization headers.

The relay observed exactly one model identifier on all chat-completions traffic
and forwarded `low` on every request; three non-chat `/v1/models` metadata calls
are excluded. All 261 chat-completions requests carried provider-reported
usage. No token value is estimated.

## 7. Measurement definitions

| Quantity | Definition | Source |
|---|---|---|
| `elapsed_s` | barrier release to agent process exit | lifecycle events |
| `api_service_s` | sum of chat-completion request durations | relay |
| `agent_busy_s` | derived: `elapsed_s − api_service_s` | derived |
| `cpu_s` | cgroup `cpu.stat usage_usec` at scope exit | cgroup snapshot |
| `cpu_user_s`, `cpu_system_s` | `cpu.stat` user/system counters | cgroup snapshot |
| peak memory | cgroup `memory.peak`; 1 s series uses `memory_current` | cgroup + samples |
| OOM kills | `memory.events oom_kill` | cgroup snapshot |
| throttling | `cpu.stat nr_throttled`, `throttled_usec` | cgroup snapshot |
| requests | chat-completion rows attributed to the trial | relay |
| tokens | summed provider-reported input/output/reasoning/cached | relay |
| cost | summed provider list price | relay |
| speed-up | pristine median / candidate median, interleaved repeats | grader metrics |
| parity | exact document equality on every hidden workload | grader metrics |

Resource sampling is 1 s (observed median 1.0000 s); the final cgroup snapshot
is authoritative. A missing snapshot would fall back to the sample maximum and
record a discrepancy; none occurred.

Aggregates are recomputed from the nine trials, never copied from the
controller's verdict:

```
quality_points           = Σ score
total_wall_s             = Σ elapsed_s
mean_success_wall_s      = mean(elapsed_s over verified passes)
total_cpu_s              = Σ cpu_s;  mean_cpu_s = mean(cpu_s)
mean_peak_mem_bytes      = int(mean(peak_mem_bytes))
nominal_cost_usd         = Σ provider list-price cost
cost_per_verified_usd    = nominal_cost_usd / verified_passes
tokens_per_quality_point = Σ tokens / quality_points
quality_per_million_tok  = quality_points / (Σ tokens / 1e6)
pass_rate                = verified_passes / attempts, 4 dp
```

The derivation re-checks tokens, list price and elapsed time against the
controller summary and verifies the run's SHA-256 seal (755 files). Published
reconciliation status is `OK` with zero discrepancies.

## 8. Measured, derived, estimated, unknown

| Category | Examples |
|---|---|
| Measured | wall time, request durations, provider token counts, cgroup CPU/memory, exit codes, HTTP statuses, grader case results, diff hashes |
| Derived | busy time, aggregates, cost per verified task, tokens per quality point, speed-ups, MiB conversions, pass rates |
| Estimated | nothing in the dataset; maintainability points are rule-based heuristics, not estimates of long-term maintainability |
| Unknown | incremental subscription cash, JCode's tool-level activity, behaviour under different provider contention, performance outside these tasks |
